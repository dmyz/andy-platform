# 架构与开发规范

本文是 UPMS 后端唯一的架构和开发规范文档。根包为 `net.junanw.upms`，当前生产代码采用四层业务域架构。

```text
net.junanw.upms
├── core
├── business
├── application
└── infrastructure
```

## 架构决策

UPMS 后端需要同时承载稳定平台能力、可扩展业务能力、后台管理端入口和公共技术基础设施。根包下固定使用四个顶层分组，不再新增其他顶层业务包。

| 分组 | 职责 | 当前模块 |
| --- | --- | --- |
| `core` | 核心平台域，承载稳定平台能力 | `identity`、`organization`、`dictionary`、`setting`、`security.audit` |
| `business` | 可扩展业务域，承载业务能力 | `content.file`、`content.announcement`、`content.message` |
| `application` | 端侧入口、请求适配、场景编排和视图组织 | `upms` 后台管理端聚合入口 |
| `infrastructure` | 基础设施和公共技术能力 | `persistence.xbatis`、`security.satoken`、`shared` |

四层之间使用允许依赖矩阵，不要求形成链式依赖：

| 来源层 | 可依赖目标 |
| --- | --- |
| `application` | `core`、`business`、`infrastructure` |
| `business` | `core`、`infrastructure` |
| `core` | `infrastructure` |
| `infrastructure` | 无业务层依赖 |

## application.upms

`application.upms` 是 UPMS 后台管理端聚合入口，所有 `/admin/**` Controller 必须放在 `src/main/java/net/junanw/upms/application/upms/**`。

当前一级功能场景包固定为：

| 包 | 场景 |
| --- | --- |
| `auth` | 登录、退出、验证码、密码、当前用户认证上下文 |
| `identity` | 用户、角色、菜单、权限等身份权限管理入口 |
| `organization` | 部门、岗位等组织管理入口 |
| `dictionary` | 字典类型、字典项管理入口 |
| `setting` | 系统参数、配置项等设置入口 |
| `audit` | 登录日志、操作日志等审计入口 |
| `content` | 公告、消息、文件等内容和支撑能力管理入口 |
| `profile` | 管理端个人中心入口 |
| `workspace` | 管理端工作台、仪表盘入口 |

`application.upms` 按管理端功能场景分包，不按底层领域包机械复制。纯管理入口可以只保留 `controller`；存在跨域聚合、当前登录用户上下文、旧接口兼容或视图组装时，再增加 `service` 和 `model/*`。

新增一级功能场景包前，必须同步更新本文档和 `.codex/skills/upms-architecture/scripts/check-architecture.sh` 白名单。

## 模块归类

### core

- `core.identity`：账号、认证、用户、角色、权限、导航、密码、验证码、在线会话、当前用户查询。
- `core.identity.permission`：权限定义与权限模块目录。权限模块目录维护权限分组编码、展示名称、层级和启停状态，供权限定义的 `module_code` 引用。
- `core.organization`：组织与成员关系。
- `core.dictionary`：字典类型与字典项。
- `core.setting`：系统配置。
- `core.security.audit`：登录审计、操作审计。

### business

- `business.content.file`：文件能力。
- `business.content.announcement`：公告能力。
- `business.content.message`：消息能力。
- `business.<domain>`：未来新增业务域。

### infrastructure

- `infrastructure.persistence.xbatis`：XBatis 基类和持久层公共能力。
- `infrastructure.security.satoken`：Sa-Token、安全配置、密码基础设施配置。
- `infrastructure.shared.api`：API 响应、分页模型。
- `infrastructure.shared.exception`：异常模型与处理。
- `infrastructure.shared.id`：ID 生成。
- `infrastructure.shared.security`：安全工具。
- `infrastructure.shared.util`：通用工具。
- `infrastructure.shared.web`：Web 过滤器、全局异常处理等。

## 依赖约束

- Controller 只依赖本模块或其他模块的 Service。
- `/admin/**` Controller 统一归入 `application.upms`，`core` 和 `business` 不承载管理端 HTTP 入口。
- `application.upms` 禁止直接依赖 Mapper、Entity 或 `QueryChain`。
- 禁止跨模块直接依赖其他模块的 Mapper 或 Entity。
- 跨模块业务协作优先通过 Service 接口。
- `infrastructure` 禁止依赖 `core`、`business`、`application` 的具体业务实现。
- `business` 和 `core` 禁止依赖 `application`。
- `core` 原则上不依赖 `business`；确有协作时优先通过应用层编排。

## 模块结构

业务模块默认采用以下结构，按需裁剪：

- `controller`
- `service`
- `mapper`
- `entity`
- `model/request`
- `model/response`
- `model/view`
- `convert`
- `enums`
- `support`

扩展目录按需增加：

- `job`
- `listener`
- `scheduler`
- `export`
- `security`

命名约定：

- 服务接口使用 `*Service`，服务实现使用 `*ServiceImpl`。
- 实体使用业务名 `*Entity`，Mapper 使用业务名 `*Mapper`。
- 请求对象使用 `*Request`，响应对象使用 `*Response`。
- 详情和列表视图使用 `*DetailView`、`*PageItem`。

## 新增模块规范

新功能必须先确定所属顶层分组：

- 身份、权限、组织、字典、系统配置、审计等平台稳定能力进入 `core`。
- 文件、公告、消息和未来可扩展业务域进入 `business`。
- UPMS 后台端入口、请求适配、跨域场景编排和视图组织进入 `application.upms`。
- Web、安全、异常、公共 API、XBatis 基类、ID、工具类等技术能力进入 `infrastructure`。

常见归位：

- 用户、角色、权限、导航管理入口放入 `application.upms.identity`。
- 登录审计、操作审计入口放入 `application.upms.audit`。
- 公告、文件、消息入口放入 `application.upms.content`。
- 个人中心入口放入 `application.upms.profile`。
- 工作台、仪表盘入口放入 `application.upms.workspace`。

禁止事项：

- 不新增 `application.admin`、`application.personal`、`application.portal` 平铺入口包。
- 不把 `/admin/**` Controller 放回 `core` 或 `business`。
- 不新增 repository 包；持久层目录统一使用 `mapper`。

## 持久层规范

当前持久层统一使用 XBatis：

- 使用 `xbatis-spring-boot-starter`，版本由 `xbatis-spring-boot-parent` 的 `1.10.1-spring-boot4` 版本线管理。
- 公共基类和持久层支撑能力位于 `infrastructure.persistence.xbatis`。
- Mapper 位于本模块 `mapper` 包，并继承 `cn.xbatis.core.mybatis.mapper.MybatisMapper<T>`。
- Service 可以使用本模块 Mapper 和 XBatis `QueryChain`。
- `application.upms` 不直接使用 Mapper、Entity 或 `QueryChain`。
- 实体类使用 `cn.xbatis.db.annotations.Table`、`TableId`、`TableField` 等 XBatis 注解。
- `Long` 类型实体主键交给 XBatis 生成器，不在业务代码中手动 `setId`。
- 逻辑删除字段使用 `deleted`，语义保持 `0=false`、`1=true`。
- 不新增 MyBatis-Flex 依赖、注解、Wrapper 或 TableDef。

数据库结构变更只通过 Flyway 脚本管理，目录为 `src/main/resources/db/migration/`。Flyway 脚本一旦执行，不要修改原脚本；后续变更创建新脚本。

## 权限模块目录

`iam_permission_module` 是权限定义的模块目录，用于维护权限分组编码、展示名称、父级编码、排序、启停状态和备注。

- `iam_permission.module_code` 引用 `iam_permission_module.module_code` 的业务编码，由 Service 层校验存在且启用。
- 当前不对 `iam_permission.module_code` 增加数据库外键，避免历史权限、种子数据和未来扩展模块被强耦合。
- 权限模块目录不是导航节点，也不是后端包名；导航访问关系仍通过 `ui_navigation_permission.permission_id` 关联权限。
- 角色授权关系仍通过 `iam_role_permission.permission_id` 关联权限，不直接关联权限模块。
- 个人中心 `profile` 是登录后公共入口，不进入权限模块目录、权限定义、角色授权或导航授权；访问只依赖 `/admin/**` 登录校验。
- 删除权限模块前必须检查是否存在子模块或未删除权限定义引用；存在引用时拒绝删除。
- 管理端入口为 `application.upms.identity.permission.controller.PermissionModuleController`，领域能力保留在 `core.identity.permission`。

## 开发规范

- 必须为新增或修改的函数、方法添加必要文档注释。
- 生产项目 Markdown 文档文件名使用中文；`README.md` 和 `AGENTS.md` 是约定入口文件，保留英文名。
- 项目根目录不存放 `scripts/`；检查脚本放在对应 `.codex/skills/*/scripts/` 目录。
- 禁止硬编码密钥、密码、令牌等敏感信息。
- 必须处理异常，避免直接暴露堆栈信息。
- 建议单行代码不超过 160 个字符。
- 跨模块返回值优先使用 request/response/view 模型，不把 Entity 暴露给 Controller 返回值。
- 动态查询优先使用 XBatis 条件能力，避免拼接 SQL 字符串。


XBatis 持久层改动必须运行：

```bash
bash .codex/skills/xbatis-usage/scripts/check-xbatis-usage.sh
```

涉及 Java 代码时按改动范围运行：

```bash
mvn -q test-compile
mvn -q test
```
